The Quality Scoreboard

fsagent, RTCP & MOS — how “it sounds bad” becomes a number

Turning complaints into numbers

“The call quality was bad.” — every support ticket ever written. That’s not a bug report; it’s a feeling.

This module is how the system turns that feeling into measurements: jitter 14ms, loss 0.8%, MOS 3.6. Meet the figure-skating judge with instruments.

While the skater (the call) performs, sensors measure every wobble. The receiver of every voice stream is already sending scorecards back, automatically. Our job is just to read them.

💡
Key Insight

Voice quality isn’t magic — it’s measured continuously. Every RTP media stream carries RTCP reports back from the receiver; fsagent reads them via FreeSWITCH events, aggregates per call leg, and exports a verdict.

The judge’s three instruments

Every wobble on the ice gets measured. Click each card to learn more:

🥁

Jitter

Packets arriving unevenly — a drummer who speeds up and slows down. Measured in milliseconds. Under 30ms? The audience can’t tell.

🕳️

Packet loss

Words that never arrive — jumps skipped entirely. Even 1–2% is audible as gaps or that robotic underwater voice.

🏅

MOS

The final scorecard — one number saying “how did it feel to watch?” Originally humans scored 1–5; now algorithms estimate it from the other two stats.

One leg, one scorecard

This is fsagent’s actual scorecard structure from fsagent/pkg/calculator/rtcp.go:

CODE — fsagent/pkg/calculator/rtcp.go 
type RTCPMetrics struct {
	Timestamp     time.Time
	InstanceName  string
	ChannelID     string // Unique-ID for per-leg monitoring
	CorrelationID string // SIP Call-ID for per-call aggregation
	DomainName    string // SIP domain for filtering by tenant/domain
	Direction     string

	Jitter      float64 // Average jitter in milliseconds
	PacketsLost int32   // Total packets lost

	PacketsSent int64 // Total packets sent
	OctetsSent  int64 // Total octets sent
}
PLAIN ENGLISH

When this reading was taken, and which FreeSWITCH server took it.

ChannelID identifies ONE side of the call — a single call leg.

CorrelationID ties both legs together into one conversation — the pair-of-skaters ID.

DomainName: multiple tenant companies share this platform, and their metrics stay separable.

The actual measurements: unevenness in ms, and packets that vanished.

How much was shipped, so loss can be computed as a percentage.

Those two IDs matter more than they look. One phone call always has two legs, and each gets its own scorecard.

Folding readings into a running average

Reports trickle in throughout the call. fsagent keeps running state per channel and folds each new reading in:

CODE — fsagent/pkg/calculator/rtcp.go 
func (rc *rtcpCalculator) AggregateMetrics(ctx context.Context, event *connection.FSEvent, direction string, instanceName string) (bool, *RTCPMetrics, error) {
	channelID := event.GetHeader("Unique-ID")
	if channelID == "" {
		return false, nil, fmt.Errorf("RTCP event missing Unique-ID")
	}

	state, err := rc.store.Get(ctx, channelID)
	if err != nil {
		logger.WarnWithFields(map[string]interface{}{
			"channel_id":  channelID,
			"fs_instance": instanceName,
			"direction":   direction,
			"error":       err.Error(),
		}, "Channel state not found for RTCP aggregation")
		return false, nil, fmt.Errorf("failed to get channel state: %w", err)
	}
PLAIN ENGLISH

Every incoming report names its channel. No name? Refuse to process it.

Look up the running state for that leg — kept in memory or Redis.

Not found? Log loudly with full context: which channel, which server, which direction.

And refuse to guess — silent wrong data is worse than no data.

Found? Fold the new numbers into the running average and continue.

Two legs, two stories

The agent-side leg and the customer-side leg of the same call each get their own scorecard. They share a CorrelationID but nothing else — one side can be crystal clear while the other sounds like a robot underwater. Per-leg (Unique-ID) tells you where; per-call (SIP Call-ID) tells you which conversation.
