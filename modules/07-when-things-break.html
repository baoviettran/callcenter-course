Your detective toolkit — evidence, rooms, and a decision tree for every incident

“phones are down??”

Take a breath. Every incident is a crime scene, and every component you met this course leaves fingerprints in a different room: SIP envelopes in packet captures, the PBX’s own diary, bulletins on the wire, scorecards on the dashboard, the written record in PostgreSQL.

The detective’s skill is not knowing everything — it is knowing which room to enter first based on the symptom. This module is the decision tree for that exact moment.

The detective’s kit

Six tools, six rooms of evidence. Each one answers a different question:

📓

fs_cli

FreeSWITCH’s interactive console. Run show channels, watch live events, ask the PBX what it is doing right now.

✉️

sngrep

A live packet capture viewer for SIP envelopes. Answers: “did the INVITE even arrive?”

📰

fsevents :9090

The health endpoint and /metrics. Is the event wire even connected? Are reconnect attempts climbing?

🗄️

Kafka lag & fsextension logs

Is the archive keeping up? Consumer lag growing means CDRs will be late or missing. fsextension logs tell you why.

📈

Grafana / Prometheus

fsagent’s scoreboard. Was quality already degrading BEFORE the outage — jitter creeping up all morning?

🚪

Kamailio logs

The front door. Did calls even get routed to FreeSWITCH, or did they die at the proxy before anyone noticed?

Symptom → first room to search

Seven classic symptoms. Click to reveal the room you enter first and why:

📞 Can’t register / phone shows offline

First room: Kamailio logs, then sngrep for REGISTER.

The common factor across every “offline” agent is registration. Something upstream — network, Kamailio, auth — is rejecting the phones before FreeSWITCH ever sees them.

🔔 Rings but never answers

First room: fs_cli, dialplan, xml_curl response from fsextension.

The call got in. The signal reached FreeSWITCH. The problem is the routing rulebook — did the dialplan get served? Did fsextension’s xml_curl return the right rules?

🤫 Connected but no audio / one-way audio

First room: sngrep for RTP endpoints, SDP/NAT addresses.

Signaling worked perfectly. The media path did not. Classic SDP/NAT territory — the negotiated media addresses in the SIP invite do not match where RTP packets actually travel.

🕳️ Calls fine but CDRs / records missing

First room: fsevents /metrics → Kafka consumer lag → database.

The calls were fine. The narration dropped. You know this from Module 4 — follow the wire backwards from the database to the source event, and you will find the gap.

🤖 Sounds terrible (robotic, choppy)

First room: Grafana / Prometheus via fsagent dashboards, per-leg comparison.

Open fsagent’s scorecards and compare legs side by side. Jitter and packet-loss graphs tell you which side of the conversation is suffering, and exactly how badly.

⚙️ Cannot add agent to queue

First room: FusionPBX web UI or fsextension management domain.

Nothing about active calls is broken — a management action is being rejected or lost. Queue membership flows IN through fsextension’s APIs, not through the telephony path.

🌊 Intermittent drops after network change

First room: Grafana dashboards for jitter/loss timeline, then sngrep for media renegotiations.

A network change mid-shift is a slow-burn clue. Grafana shows exactly when quality started slipping; sngrep shows whether calls are being re-INVITEd or silently failing.

Reading the fingerprints

Two pieces of evidence you will touch on nearly every incident. First, the wire’s health fingerprint — you met it in Module 4, now read it like a detective:

CODE — fsevents/internal/esl/client.go 
type ConnectionStats struct {
	ConnectedAt       time.Time
	EventsReceived    uint64
	EventsProcessed   uint64
	ReconnectAttempts uint64
	LastError         error
	mu                sync.RWMutex
}
PLAIN ENGLISH

If Received ≫ Processed, backlog is growing — consumers too slow, records arriving late.

If ReconnectAttempts climbs, the wire keeps dropping — expect data gaps in every downstream system.

ConnectedAt tells you if the process restarted recently without anyone planning it.

LastError names the culprit: refused connection, timeout, auth failure…

Second, the PBX’s own diary. A real fs_cli session:

TERMINAL — fs_cli 
freeswitch@pbx> show channels count
0 total, 0 active

freeswitch@pbx> version
FreeSWITCH Version 1.10.8 (git abc123)
PLAIN ENGLISH

Ask: how many calls exist right now? Answer: zero total, zero active.

If Slack says “phones are down” but agents say calls connect — reconcile those two stories here, live.

Ask: which build am I running? Useful after deploys — “did we just change anything?” starts here.
