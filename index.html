Layer 3 — The Dispatchers

Lua Scripts

Lua scripts are the custom dispatchers — they decide which train goes where when the standard dialplan doesn't cover it.

pbx/fs/resources/lua/bridge_to_agent.lua 
local agent_uuid = argv[1] or ''
local dialplan_id = argv[2] or ''

if not session or not session:ready() or agent_uuid == '' then
    return false
end

local api = freeswitch.API()

The script first checks: is the call still alive? Is there an agent ID? Then it opens a database connection. If the database is down, it logs a warning and bails — never try to bridge a call without knowing the agent's status.

Layer 3 — Cascade Routing

Trying Multiple Queues

Cascade routing tries multiple queues in order. If queue #1 has no available agents, it falls through to queue #2, then #3, and so on.

CODE 

local args = argv[1] or ""
local dialplan_id = argv[2] or ""

if args == "" then
    freeswitch.consoleLog("ERR",
        "[queue_cascade] Không có queue_ids
        được truyền vào")
    return
end

local queue_ids = {}
for id in string.gmatch(args, "([^,]+)") do
    id = id:match("^%s*(.-)%s*$") -- trim
    if id ~= "" then
        table.insert(queue_ids, id)
    end
end
PLAIN ENGLISH

Receive a comma-separated string of queue IDs as the first argument from FreeSWITCH...

If no queues were passed, log an error (Vietnamese: "no queue_ids were provided") and bail out...

Build an ordered list by splitting the string on commas...

Trim whitespace from each ID so "q1, q2" and "q1,q2" both work...

Add each valid ID to the queue_ids array. The order matters — cascade tries them left to right.

The Control Tower

The Java brain behind the telephony brawn.

The Java brain behind the telephony brawn

Module 2 showed you the engine that makes calls happen. But who decides how calls are routed? Who keeps the list of agents, queues, and extensions? Who remembers every call after it ends?

That is fsextension — the management layer that sits between humans configuring the system and FreeSWITCH executing calls. Think of it as an air traffic control tower. FreeSWITCH is the runway where planes actually land, but fsextension is the tower — it decides which planes land where, keeps the flight plan database, pushes updated schedules to the runway, and records every landing in the logbook.

📋
Why should I care?

When someone says “I added a new queue but calls are not routing to it,” the problem is almost certainly in fsextension. Understanding its architecture means you know exactly where to look.

Spring Boot: the framework that builds the backend

fsextension is built on Spring Boot — a Java framework that handles the boring plumbing so developers can focus on business logic. Its entry point is a single annotated class, and its controllers receive REST API requests and route them to the right handler.

Here is the controller that handles dialplan scripts. Notice how every request flows through the command bus:

CODE 
@PostMapping("/script")
public Boolean createScript(
        @RequestBody GenerateScriptCommand cmd,
        @RequestHeader("Domain-Name") String domainName) throws JsonProcessingException {

    cmd = cmd.domainName(domainName);
    log.debug("createScript > Script with id: {} data: {}", cmd.getUniqueId(), objectMapper.writeValueAsString(cmd));

    return bus.execute(cmd);
}
PLAIN ENGLISH

When someone POSTs a new dialplan script…

…this method receives the HTTP request and its JSON body.

The Domain-Name header tells us which tenant (client) this is for — this is a multi-tenant system.

Stamp the command with the tenant’s domain name…

…log the details for debugging…

…and hand it to the command bus. The bus.execute(command) is CQRS — commands go IN through this door, queries come OUT through another. Never mixed.

CQRS: commands go IN, queries come OUT

CQRS is an architectural pattern that separates two fundamentally different operations: changing data (commands) and reading data (queries). In fsextension, every HTTP endpoint that creates or updates something goes through bus.execute(command).

Here is another example — registering a new phone number follows the exact same pattern:

CODE 
@PostMapping("/dialed-number")
public UUID createDialedNumber(
        @RequestHeader("Domain-Name") String domainName,
        @RequestAttribute("Domain-Id") String domainId,
        @RequestBody CreateDialedNumberCommand command) {

    if (command.getDomainId() == null) {
        command = command.domainId(domainId);
    }

    return bus.execute(command).getId();
}
PLAIN ENGLISH

Registering a new phone number (dialed number) follows the same pattern.

The domain is extracted from HTTP headers — this is how the system knows which tenant owns the number.

If the command did not already carry a domain ID, stamp it with the one from the request.

Hand the command to the bus. Same door, same pattern, every time.

🎯
Why separate commands from queries?

Commands change state and need validation, logging, and authorization. Queries are read-only and can be cached or optimized independently. Mixing them makes it hard to scale reads vs. writes — and that is exactly what CQRS solves.

SFTP and Flyway: the plumbing behind the scenes

Two more pieces of the puzzle that keep fsextension running smoothly:

📥

SFTP Provisioning

fsextension pushes dialplan XML and recordings to FreeSWITCH via mod_xml_curl. When FreeSWITCH needs to know how to route a call, it fetches the dialplan from fsextension over HTTP, or fsextension pushes it proactively via SFTP. Either way, the dialplan stays in sync.

🗃

Flyway Migrations

When fsextension needs a new database table or column, the change is defined as a migration — a numbered SQL file. Flyway applies them in order, tracks which ones have run, and never re-runs an old one. This means the database schema evolves safely across deployments without anyone losing data.

The SharedWorker pattern

A WebWorker is a script that runs in a background thread, separate from the main page. A SharedWorker goes further: it is one worker instance shared by every tab of the same site.

Each tab connects to the worker through a PostMessage channel — a form of IPC (Inter-Process Communication). The worker holds the single SIP registration and the single Socket connection, and routes messages to whichever tab needs them.

    if (sipCore) {
      console.log(`Auto-hanging up call ${callId} due to: ${reason}`);
      await sipCore.hangupCall(callId);
    } else {
      console.error(`Cannot hangup call ${callId}: SipCore not initialized`);
    }
  },
  onAudioContextStateChanged: (hasRunningAudioContext: boolean, previousState: boolean) => {
    if (sipCore) {
      console.log(`AudioContext state changed: ${previousState} → ${hasRunningAudioContext}`);
      sipCore.handleAudioContextStateChange(hasRunningAudioContext, previousState);
    }
  }
});
PLAIN ENGLISH

The TabManager receives two callbacks: one for when a tab closes during a call (auto-hang-up), and one for when audio state changes (resume or suspend).

onTabClosedWithCall: if a tab closes while on a call, the worker automatically hangs up — no orphaned SIP session left behind.

onAudioContextStateChanged: the browser may suspend audio after idle. When audio resumes, the worker notifies SipCore so it can re-establish the audio path.

shared.io: Socket.IO over SharedWorker

shared.io creates four managers: MessageRouter directs messages, AckManager tracks request/response pairs, NotificationManager broadcasts events to all tabs, and LongPollingManager provides a long-polling fallback for browsers without SharedWorker support.

When a tab connects, it sends a PostMessage port — the worker uses this private channel to talk to that specific tab.

SocketManager: the gateway

The SocketManager interface is the gateway between the SharedWorker and the Socket.IO server. Every tab calls connect, emit, on through this single manager.

The key method is emitWithAck — the ACK-based request/response pattern: send a message and wait for the server to acknowledge it.

shared.io/src/worker/socket-manager.ts 
export interface ISocketManager {
  connect(url: string, options: SharedSocketIOOptions, message: WorkerMessage): void;
  disconnect(message: WorkerMessage): void;
  emit(eventName: string, args: any[], message: WorkerMessage): void;
  emitWithAck(eventName: string, args: any[], message: WorkerMessage): Promise<any>;
  on(eventName: string, message: WorkerMessage): void;
  off(eventName: string, message: WorkerMessage): void;
  once(eventName: string, message: WorkerMessage): void;
  getConnectionStatus(): ConnectionStatus;
}
PLAIN ENGLISH

connect / disconnect: open or close the Socket.IO connection to the backend server.

emit: fire-and-forget — send a message to the server without waiting for a response.

emitWithAck: request/response — send a message and get a Promise that resolves when the server acknowledges it. This is how reliable data flows work.

on / off / once: subscribe, unsubscribe, or listen once to server events — the same pattern as a DOM event listener.

getConnectionStatus: check whether the socket is currently connected, reconnecting, or disconnected.

How they work together

sip.js-worker handles the call lifecycle: ringing, answering, talking, hanging up. shared.io handles everything else: agent status updates, queue notifications, CDR display.

They are independent — either can work without the other — but together they give the browser agent a complete real-time experience that survives tab switches.

📡

sip.js-worker owns

SIP registration with FreeSWITCH. Call setup (INVITE). Call teardown (BYE). WebRTC media negotiation. AudioContext state management.

🔌

shared.io owns

Agent status (available, on-call, break). Queue notifications (new call waiting). CDR display (call records). Any real-time data the UI needs to stay in sync with the backend.

The Quality Scoreboard

fsagent, RTCP & MOS — how “it sounds bad” becomes a number

Turning complaints into numbers

“The call quality was bad.” — every support ticket ever written. That’s not a bug report; it’s a feeling.

This module is how the system turns that feeling into measurements: jitter 14ms, loss 0.8%, MOS 3.6. Meet the figure-skating judge with instruments.

While the skater (the call) performs, sensors measure every wobble. The receiver of every voice stream is already sending scorecards back, automatically. Our job is just to read them.

💡
Key Insight

Voice quality isn’t magic — it’s measured continuously. Every RTP media stream carries RTCP reports back from the receiver; fsagent reads them via FreeSWITCH events, aggregates per call leg, and exports a verdict.

The judge’s three instruments

Every wobble on the ice gets measured. Click each card to learn more:

🥁

Jitter

Packets arriving unevenly — a drummer who speeds up and slows down. Measured in milliseconds. Under 30ms? The audience can’t tell.

🕳️

Packet loss

Words that never arrive — jumps skipped entirely. Even 1–2% is audible as gaps or that robotic underwater voice.

🏅

MOS

The final scorecard — one number saying “how did it feel to watch?” Originally humans scored 1–5; now algorithms estimate it from the other two stats.

One leg, one scorecard

This is fsagent’s actual scorecard structure from fsagent/pkg/calculator/rtcp.go:

How much was shipped, so loss can be computed as a percentage.

Those two IDs matter more than they look. One phone call always has two legs, and each gets its own scorecard.

Folding readings into a running average

Reports trickle in throughout the call. fsagent keeps running state per channel and folds each new reading in:

CODE — fsagent/pkg/calculator/rtcp.go 
func (rc *rtcpCalculator) AggregateMetrics(ctx context.Context, event *connection.FSEvent, direction string, instanceName string) (bool, *RTCPMetrics, error) {
	channelID := event.GetHeader("Unique-ID")
	if channelID == "" {
		return false, nil, fmt.Errorf("RTCP event missing Unique-ID")
	}

	state, err := rc.store.Get(ctx, channelID)
	if err != nil {
		logger.WarnWithFields(map[string]interface{}{
			"channel_id":  channelID,
			"fs_instance": instanceName,
			"direction":   direction,
			"error":       err.Error(),
		}, "Channel state not found for RTCP aggregation")
		return false, nil, fmt.Errorf("failed to get channel state: %w", err)
	}
PLAIN ENGLISH

Every incoming report names its channel. No name? Refuse to process it.

Look up the running state for that leg — kept in memory or Redis.

Not found? Log loudly with full context: which channel, which server, which direction.

And refuse to guess — silent wrong data is worse than no data.

Found? Fold the new numbers into the running average and continue.

The detective’s kit

FreeSWITCH’s interactive console. Run show channels, watch live events, ask the PBX what it is doing right now.

Symptom → first room to search

Seven classic symptoms. Click to reveal the room you enter first and why:

📞 Can’t register / phone shows offline

First room: Kamailio logs, then sngrep for REGISTER.

The common factor across every “offline” agent is registration. Something upstream — network, Kamailio, auth — is rejecting the phones before FreeSWITCH ever sees them.

🔔 Rings but never answers

First room: fs_cli, dialplan, xml_curl response from fsextension.

The call got in. The signal reached FreeSWITCH. The problem is the routing rulebook — did the dialplan get served? Did fsextension’s xml_curl return the right rules?

🤫 Connected but no audio / one-way audio

First room: sngrep for RTP endpoints, SDP/NAT addresses.

Signaling worked perfectly. The media path did not. Classic SDP/NAT territory — the negotiated media addresses in the SIP invite do not match where RTP packets actually travel.

🕳️ Calls fine but CDRs / records missing

First room: fsevents /metrics → Kafka consumer lag → database.

The calls were fine. The narration dropped. You know this from Module 4 — follow the wire backwards from the database to the source event, and you will find the gap.

🤖 Sounds terrible (robotic, choppy)

First room: Grafana / Prometheus via fsagent dashboards, per-leg comparison.

Open fsagent’s scorecards and compare legs side by side. Jitter and packet-loss graphs tell you which side of the conversation is suffering, and exactly how badly.

⚙️ Cannot add agent to queue

First room: FusionPBX web UI or fsextension management domain.

Nothing about active calls is broken — a management action is being rejected or lost. Queue membership flows IN through fsextension’s APIs, not through the telephony path.

🌊 Intermittent drops after network change

First room: Grafana dashboards for jitter/loss timeline, then sngrep for media renegotiations.

A network change mid-shift is a slow-burn clue. Grafana shows exactly when quality started slipping; sngrep shows whether calls are being re-INVITEd or silently failing.
