The Control Tower

The Java brain behind the telephony brawn.

The Java brain behind the telephony brawn

Module 2 showed you the engine that makes calls happen. But who decides how calls are routed? Who keeps the list of agents, queues, and extensions? Who remembers every call after it ends?

That is fsextension — the management layer that sits between humans configuring the system and FreeSWITCH executing calls. Think of it as an air traffic control tower. FreeSWITCH is the runway where planes actually land, but fsextension is the tower — it decides which planes land where, keeps the flight plan database, pushes updated schedules to the runway, and records every landing in the logbook.

📋
Why should I care?

When someone says “I added a new queue but calls are not routing to it,” the problem is almost certainly in fsextension. Understanding its architecture means you know exactly where to look.

Spring Boot: the framework that builds the backend

fsextension is built on Spring Boot — a Java framework that handles the boring plumbing so developers can focus on business logic. Its entry point is a single annotated class, and its controllers receive REST API requests and route them to the right handler.

Here is the controller that handles dialplan scripts. Notice how every request flows through the command bus:

CODE 
@PostMapping("/script")
public Boolean createScript(
        @RequestBody GenerateScriptCommand cmd,
        @RequestHeader("Domain-Name") String domainName) throws JsonProcessingException {

    cmd = cmd.domainName(domainName);
    log.debug("createScript > Script with id: {} data: {}", cmd.getUniqueId(), objectMapper.writeValueAsString(cmd));

    return bus.execute(cmd);
}
PLAIN ENGLISH

When someone POSTs a new dialplan script…

…this method receives the HTTP request and its JSON body.

The Domain-Name header tells us which tenant (client) this is for — this is a multi-tenant system.

Stamp the command with the tenant’s domain name…

…log the details for debugging…

…and hand it to the command bus. The bus.execute(command) is CQRS — commands go IN through this door, queries come OUT through another. Never mixed.

CQRS: commands go IN, queries come OUT

CQRS is an architectural pattern that separates two fundamentally different operations: changing data (commands) and reading data (queries). In fsextension, every HTTP endpoint that creates or updates something goes through bus.execute(command).

Here is another example — registering a new phone number follows the exact same pattern:

CODE 
@PostMapping("/dialed-number")
public UUID createDialedNumber(
        @RequestHeader("Domain-Name") String domainName,
        @RequestAttribute("Domain-Id") String domainId,
        @RequestBody CreateDialedNumberCommand command) {

    if (command.getDomainId() == null) {
        command = command.domainId(domainId);
    }

    return bus.execute(command).getId();
}
PLAIN ENGLISH

Registering a new phone number (dialed number) follows the same pattern.

The domain is extracted from HTTP headers — this is how the system knows which tenant owns the number.

If the command did not already carry a domain ID, stamp it with the one from the request.

Hand the command to the bus. Same door, same pattern, every time.

🎯
Why separate commands from queries?

Commands change state and need validation, logging, and authorization. Queries are read-only and can be cached or optimized independently. Mixing them makes it hard to scale reads vs. writes — and that is exactly what CQRS solves.

Kafka: the event streaming backbone

This class configures Kafka — the message delivery system between components.

@Conditional means Kafka is optional. If Kafka is not running, fsextension still works — just without event streaming.

These fields hold the Kafka topics (named channels) and connection settings.

The topics — call_recording and call_aggregated — are named channels where specific types of CDR events flow.

This consumer listens on the json_cdr Kafka topic for call detail records.

First gate: Kafka must be available (the @Conditional annotation).

Second gate: the config flag app.json_cdr_queued must be set to true.

Double-gating means the system degrades gracefully — if Kafka is down, CDRs still get processed another way (direct file import). Nothing breaks.

💡
Graceful degradation

Two independent conditions must be true for this consumer to activate. If either fails, the system falls back to a simpler path instead of crashing. This is a common pattern in production systems — always have a Plan B.

SFTP and Flyway: the plumbing behind the scenes

Two more pieces of the puzzle that keep fsextension running smoothly:

📥

SFTP Provisioning

fsextension pushes dialplan XML and recordings to FreeSWITCH via mod_xml_curl. When FreeSWITCH needs to know how to route a call, it fetches the dialplan from fsextension over HTTP, or fsextension pushes it proactively via SFTP. Either way, the dialplan stays in sync.

🗃

Flyway Migrations

When fsextension needs a new database table or column, the change is defined as a migration — a numbered SQL file. Flyway applies them in order, tracks which ones have run, and never re-runs an old one. This means the database schema evolves safely across deployments without anyone losing data.
