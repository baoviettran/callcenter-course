Layer 1 — The Engine

FreeSWITCH + Docker

The entire telephony stack runs inside Docker containers. The docker-compose file defines two services: the database and FreeSWITCH itself.

pbx/docker-compose-host.yml 
services:
  postgres:
    image: luongld/postgres:14
    container_name: postgres_140
  pbx:
    image: luongld/pbx:1.10.8
    container_name: pbx_1108
💡
Two Containers, One System

The postgres container holds the shared database. The pbx container runs FreeSWITCH with custom modules like mod_callcenter for queue management. The pbx image is custom-built with patched modules for this platform.

Layer 2 — The Admin Panel

FusionPBX

FusionPBX is a PHP web application with its own MVC architecture. Every page request starts at one entry point.

fusionpbx/index.php 
//includes files
require_once __DIR__ . "/resources/require.php";

//if logged in, redirect to login destination

This single line loads FusionPBX's entire framework — database connections, authentication checks, and routing rules. Think of it as the front door of the admin panel.

💡
Why This Matters for Debugging

When someone says "the admin panel is down," you need to know: is it the PHP application (FusionPBX), the database it connects to (PostgreSQL), or the web server (nginx) in front of it? Each has different symptoms and different fixes.

Layer 3 — The Dispatchers

Lua Scripts

Lua scripts are the custom dispatchers — they decide which train goes where when the standard dialplan doesn't cover it.

pbx/fs/resources/lua/bridge_to_agent.lua 
local agent_uuid = argv[1] or ''
local dialplan_id = argv[2] or ''

if not session or not session:ready() or agent_uuid == '' then
    return false
end

local api = freeswitch.API()
local Database = require "resources.functions.database"
local switch = Database.new("switch")

if not switch:connected() then
    freeswitch.consoleLog('WARN', '[bridge_to_agent] Database not connected!\n')
    return
end

The script first checks: is the call still alive? Is there an agent ID? Then it opens a database connection. If the database is down, it logs a warning and bails — never try to bridge a call without knowing the agent's status.

Code Reading

Reading the Agent Query

This is the core logic of bridge_to_agent.lua — the database query that checks whether an agent is actually available before connecting a call.

CODE 

switch:query("select agt.name name, agt.contact contact,
    agt.status status, agt.state state \
    from agents agt \
    inner join sip_registrations sreg
    on split_part(agt.contact, 'user/', 2)
    = (sreg.sip_username || '@' ||
    sreg.sip_realm) \
    where agt.name = :agent_uuid", {
    agent_uuid = agent_uuid
}, function(row)
    local agent_status = row.status or ''
    local agent_state = row.state or ''
    ...
    -- Check agent available trước khi dial
    if agent_status ~= 'Available' or
       agent_state ~= 'Waiting' then
        freeswitch.consoleLog("DEBUG",
            "[bridge_to_agent] Agent " ..
            agent_uuid .. " không sẵn sàng,
            status=" .. agent_status ..
            " state=" .. agent_state .. "\n")
        return
    end
PLAIN ENGLISH

Query the database for the agent's name, contact info, status, and state...

Join with SIP registrations to verify the agent's phone is actually connected to the server...

Match by agent UUID — the unique ID passed into this script by FreeSWITCH...

Get the status and state fields from the query result, defaulting to empty string if null...

The Vietnamese comment says "check agent available before dial" — this is the key gate...

If the agent is NOT in Available/Waiting state, stop. Don't waste a ring attempt on someone who is on another call or offline. Log why and return early.

Layer 3 — Cascade Routing

Trying Multiple Queues

Cascade routing tries multiple queues in order. If queue #1 has no available agents, it falls through to queue #2, then #3, and so on.

CODE 

local args = argv[1] or ""
local dialplan_id = argv[2] or ""

if args == "" then
    freeswitch.consoleLog("ERR",
        "[queue_cascade] Không có queue_ids
        được truyền vào")
    return
end

local queue_ids = {}
for id in string.gmatch(args, "([^,]+)") do
    id = id:match("^%s*(.-)%s*$") -- trim
    if id ~= "" then
        table.insert(queue_ids, id)
    end
end
PLAIN ENGLISH

Receive a comma-separated string of queue IDs as the first argument from FreeSWITCH...

If no queues were passed, log an error (Vietnamese: "no queue_ids were provided") and bail out...

Build an ordered list by splitting the string on commas...

Trim whitespace from each ID so "q1, q2" and "q1,q2" both work...

Add each valid ID to the queue_ids array. The order matters — cascade tries them left to right.

Layer 4 — The Security Guard

Fail2ban

Fail2ban monitors log files for failed authentication attempts. When an IP crosses the threshold, it adds a firewall rule to block that IP entirely.

pbx/f2b/Dockerfile 
ARG FAIL2BAN_VERSION="0.11.2"

FROM alpine:3.15

ARG FAIL2BAN_VERSION
RUN apk --update --no-cache add \
    bash curl grep \
    ipset iptables \
...
ENTRYPOINT [ "/entrypoint.sh" ]
CMD [ "fail2ban-server", "-f",
      "-x", "-v", "start" ]
pbx/f2b/resources/jail.local 
[freeswitch]
enabled  = true
port     = 5060:5091
protocol = all
filter   = freeswitch
logpath  = /var/log/freeswitch/freeswitch.log
action   = iptables-allports[name=freeswitch,
             protocol=all]
maxretry = 10
findtime = 60
bantime  = 3600

Fail2ban runs in its own Alpine Linux container with iptables for IP blocking. The jail configuration tells it exactly what to watch and when to act.

Code Reading

Reading the Jail Config

This is the Fail2ban jail for FreeSWITCH — every setting controls a different aspect of the ban behavior.

CODE 

[freeswitch]
enabled  = true
port     = 5060:5091
protocol = all
filter   = freeswitch
logpath  = /var/log/freeswitch/freeswitch.log
action   = iptables-allports[name=freeswitch,
             protocol=all]
maxretry = 10
findtime = 60
bantime  = 3600
PLAIN ENGLISH

Name this jail "freeswitch" — each service gets its own jail block...

This jail is active. Set to false to disable it without removing the config...

Watch SIP traffic on ports 5060 through 5091...

Monitor all protocols (TCP, UDP) — SIP can use either...

Use the freeswitch filter — a pattern file that defines what counts as a failed attempt...

Read the FreeSWITCH log file to find failed authentication entries...

When triggered, block the IP on ALL ports using iptables — not just SIP...

Allow 10 failures before banning — this is the threshold...

Count failures within 60 seconds — if 10 failures happen in a minute, trigger the ban...

Ban for 1 hour (3600 seconds) — then automatically unblock the IP.
