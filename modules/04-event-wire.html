The Client That Listens

How fsevents connects to FreeSWITCH and keeps track of its own health

CODE 
func NewClientWithBuffer(config *config.ESLConfig, bufferSize int, logger *zap.Logger) *Client {
    ctx, cancel := context.WithCancel(context.Background())

    return &Client{
        config: config,
        logger: logger.Named("esl"),
        events: make(chan *types.Event, bufferSize), // Configurable buffer for events
        stats: &ConnectionStats{
            ConnectedAt: time.Now(),
        },
        ctx:    ctx,
        cancel: cancel,
    }
}
PLAIN ENGLISH

Create a new ESL client that connects to FreeSWITCH.

Set up a cancel-able context — a way to shut the whole thing down cleanly later.

 

Start building the client object with all its pieces.

Save the connection config (host, port, etc.).

Give the logger a label so its messages say "esl" at the start.

This is the key line: events is a buffered channel — a waiting room with bufferSize chairs. If FreeSWITCH shouts faster than we can write, extra bulletins queue up here instead of being lost — until the chairs run out.

Set up the health tracker, noting when we first connected.

 

Hand back the ready-to-use client.

 

CODE 
type ConnectionStats struct {
    ConnectedAt       time.Time
    EventsReceived    uint64
    EventsProcessed   uint64
    ReconnectAttempts uint64
    LastError         error
    mu                sync.RWMutex
}
PLAIN ENGLISH

The health report card of the whole wire.

When did we first connect?

How many events came in from FreeSWITCH?

How many did we actually process and forward?

How many times did the connection drop and we had to reconnect?

What was the last error message?

A lock so multiple goroutines can safely read/write these stats at the same time.

Key insight: If EventsReceived is way ahead of EventsProcessed, your backlog is growing. If ReconnectAttempts > 0 recently, FreeSWITCH restarted or the network blipped — expect an event gap in your data.

Where Events Go From Here

Three downstream consumers, each with a different job

WS
fsevents → HTTP Endpoints

Forwards events to downstream services via HTTP with automatic retries. If an endpoint is down, the event gets queued and retried — it does not drop.

AR
fsextension consumes Kafka

Reads Avro-encoded events from Kafka topics and writes them into PostgreSQL tables: CDRs, active calls, agent history.

SD
fsagent subscribes for RTCP

Ignores most call events and instead subscribes specifically to real-time performance metrics (jitter, packet loss, MOS scores) for live quality dashboards.

CODE 
@PostMapping("/dialed-number")
public UUID createDialedNumber(
        @RequestHeader("Domain-Name") String domainName,
        @RequestAttribute("Domain-Id") String domainId,
        @RequestBody CreateDialedNumberCommand command) {

    if (command.getDomainId() == null) {
        command = command.domainId(domainId);
    }

    return bus.execute(command).getId();
}
PLAIN ENGLISH

This is a Spring Boot POST endpoint at the path "/dialed-number".

Create a new dialed number and return its unique ID.

Read the domain name from the request header.

Read the domain ID that was attached to this request by middleware.

Read the full command object from the request body.

 

If the command did not include a domain ID, fill it in from the request.

 

Execute the command via the event bus and return the new number's ID.

Two directions, two doors: Events flow OUT of FreeSWITCH on the ESL wire. But management actions — like registering a new dialed number — flow IN through REST APIs. fsextension handles both.
